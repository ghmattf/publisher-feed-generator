# Decisions, assumptions and open items

Status: plugin v0.6.0 feature-complete for the agreed scope; all automated checks pass (`tests/run-all.sh`). The owner has tested it on a real WordPress site, with real signer apps and against the live Music Index API, including searching by feed address (all OK, 2026-11-13).

## Product decisions (stated by the owner)
- Versioning: the plugin is at **0.6.0** (0.5.3 on 2026-11-14; 0.5.2 on 2026-11-14; 0.5.1 on 2026-11-14; 0.5.0 on 2026-11-14; 0.4.2 on 2026-11-14; 0.3.0 on 2026-11-13; 0.2.0 was decided 2026-11-12, replacing an earlier 1.0.0 string that was never tagged or released). Major version changes (including moving to 1.0.0) need the owner's explicit approval. Features and fixes before that are minor/patch bumps (0.3.0, 0.2.1).
- Publisher feeds only (`podcast:medium` publisher). Not albums or tracks.
- Two modes. Anonymous: create, edit, export, no login (paste-XML import was removed from the page on 2026-11-13: the "Edit an existing feed" card and screen are gone, `Core.parseXml` and its tests stay). Hosted: Nostr login (browser extension via NIP-07, or remote signer via NIP-46), feeds hosted on phafe.com.
- Whole-feed import (now not reachable from the page, see above) was by **pasted XML only**. No URL import. Importing into hosting is not an option.
- The `podcast:txt purpose="npub"` value in a feed does not need to match the login key (a convention for this generator only).
- Sign-in options (decided 2026-11-12): browser extension (NIP-07, `window.nostr`, for example Alby or nos2x), pasted `bunker://` link, QR code (NIP-46). The extension tab is first and preselected when `window.nostr` is detected, otherwise last (with a "Check again" button). Still Nostr only. `window.nostr` is looked up on every call, never cached, and only a flag (no key) is kept in `sessionStorage`. The server is unchanged: login and fresh signatures are the same NIP-98 events whichever signer produced them.
- Hosted accounts live in their own table keyed by npub, not WordPress users.
- No cross-feed approval flow: a label etc. sends the exact text (snippet) to whoever controls the other feed.
- No non-Nostr login fallback.
- Roles follow Podcast Index namespace PR #793 (`rel` is a space-separated role set; both sides must list the same set to be confirmed; if one side omits `rel` the link is kept). `studio` and `engineer` are built-in tokens too (2026-11-13), so the role picker offers artist host author label producer network hosting sponsor songwriter composer musician studio engineer; more can be added in Settings.
- `podcast:value method="lnaddress"` is the default payment method (confirmed by the owner, 2026-11-11).
- Project and plugin name is **Publisher Feed Generator** (decided 2026-11-11). Naming scheme: plugin folder/slug and text domain `publisher-feed-generator`, main file `publisher-feed-generator.php`, main class `Publisher_Feed_Generator`, shortcode `[publisher_feed_generator]`, code prefix `pfg` / `PFG_` (classes, constants, options, DB tables `pfg_*`, REST namespace `pfg/v1`, cookie `pfg_session`, headers `X-PFG-*`, JS globals `PFG*`, CSS `.pfg-*`). Nothing was live, so there is no migration from the old `mspf_*` names.
- Website and Image URL accept `http://` as well as `https://` (decided 2026-11-12; Nostr profiles often use http). Every other URL (feed URLs, support link, release feed/image URLs) stays https-only.
- New hosted feed: after Nostr sign-in the form is prefilled from the user's Nostr profile (kind 0): name -> Name / title and Author, about -> Description, website -> Website, picture -> Image URL, lud16 -> one `lnaddress` payment recipient (split 100 minus the platform share), signed-in npub -> Your npub. Only empty fields are filled, only for new hosted feeds, never anonymous mode. `lud06` (LNURL) is ignored. The profile is read by the browser from relays (no server fetch, no signing).
- "Get your npub" button under the npub field: fills from the signed-in account, otherwise asks a signer app for its public key (bunker link or QR), without creating a hosted session, and forgets the signer afterwards.
- "Save and publish" does **not** send a podping. The plugin has no podping code. Not added (it would be a new feature: needs a Podping account/token and a decision on when to ping).
- Example reference feeds (live on phafe.com, read-only for us): `Phafe.xml` (publisher), `mezzaforte.xml` (artist publisher), the album feed `some_songs.xml` (GUID 07adf84f-c1fa-47a7-a121-0fb544e859bd). Updating those feeds is out of scope.

## Editor changes (2026-11-12, owner request)
- **Feed name** is only the file name (`.../<name>/<name>.xml`). It is made from Name / title while the user types (accents removed, `&` becomes "and", max 40, must be a valid name) until the user types their own. Still fixed after saving; a taken name is reported on that field.
- **Category** and **Language** are drop-down lists (lists in `pfg-core.js`: `CATEGORIES`, `LANGUAGES`). A value from an imported feed that is not in the list is kept as an extra option.
- **Author** (`itunes:author`, now not in the form, see below) was the public creator name shown in apps. **Owner** is `itunes:owner` (name + email), a contact for directories, not shown to listeners.
- **Support the developers (optional)**: replaces the fixed platform row and the admin option "apply to exports". Shown in **both modes** (owner answer). Each configured recipient has an editable split 0-99 (default 1); 0 leaves it out. Per feed the model stores `support: [{address, split}]`; the server takes name, address and type from Settings only and ignores unknown addresses. User recipients must total 100 minus the support total; support total must stay under 100. Imported feeds keep exactly their own splits (`liftSupport`). With no own recipients there is no value block. Support splits are part of the payment fingerprint (HTTP 428).
- **Release search**: one search box and the hint "Search by name or paste the feed url above." The paste box and "Read feed" button are gone, so pasting XML into a release is no longer possible. A pasted https address is first looked up in Music Index (exact `feedUrl` match), otherwise the server reads the feed itself. The address is sent to the Music Index search as the normal `q` parameter (tested OK by the owner, 2026-11-13); if it ever finds no exact match, the fallback reads the feed directly.
- **Release heading** reads "<title> by <artist>" when an artist is known (2026-11-13). Artist = the release feed's publisher link with `rel="artist"`, else its first publisher link; the name is our own title if that link is this feed, a `title` attribute on the link if present, otherwise the editor asks the server to read that publisher feed (same fetch as release feeds) and uses its channel title. If none of that gives a name: the Music Index artist from the search result, then the first `podcast:person`. Shown only for releases read or picked in this session, not stored in the feed. **Assumption:** reading the artist's publisher feed is one extra server fetch per release; failures are silent.
- **Artist** is a read-only field at the top of the feed details (display only, not saved). When a release feed already lists this feed with roles, those roles are selected by default if the creator had not chosen any.
- **Feed details** of a release (Title, Type, Feed GUID, Feed URL, Cover image URL) are grouped under a "Show feed details" / "Hide feed details" button, hidden by default; a validation error on any of them opens it.
- **Form sections** (2026-11-13) work as an accordion: only Basics is open at first, opening one closes the others, and every section but the last ends with a Next button that opens the next one. Opening a section by clicking its title also scrolls it to the top, like Next. A failed save/download opens the section with the first error. A Nostr-profile Lightning address no longer opens Payments by itself (the banner says it was filled).
- **Author and Keywords removed from the form** (2026-11-13): nothing in the plugin requires them (only an optional tip existed, now removed). Values already in an imported feed are kept and exported unchanged, but cannot be edited. The Nostr profile name now fills Name / title only. **Owner name / Owner email** are labelled **Feed creator/editor** / **Feed contact email**; the XML is unchanged (`itunes:owner` / `itunes:name` / `itunes:email`), only labels and error messages differ.
- **Start screen** (2026-11-13): the page title is an h1 (now "Get your music credits linked!", changed 2026-11-16); the app now has its own background so its text is readable on any site theme (it was white on a yellow theme in dark mode); the intro is one sentence; the first card is "Hosted feeds" with a purple "Get started" button ("My feeds" when signed in); the second is "Want to self-host?" with a plain "Start" button; the "Edit an existing feed" card and screen are removed.
- **Editor changes 2026-11-13 (owner to-do 7-12):** Category field is hidden (the value stays Music; imported or existing values are kept). npub label is "Include npub in the feed? (optional)". Signed in with Nostr, the anonymous editor's address field is labelled just "Feed URL" (assumption: that is what "assume it will be hosted" means; hosted editors already say "Feed URL"). Leaving Basics (Next, or opening another section) is refused until Name / title and Description are filled in; errors show on those fields. A "Generate GUID" button sits under the GUID field: UUIDv5 of the feed URL when there is one, otherwise a random UUID (assumption about what "generate GUID" meant; the GUID still also fills in automatically from the feed URL). The "Downloaded ... Upload it to ..." message shows under the Download button instead of at the top.
- **Settings > Roles** (2026-11-13) shows the built-in roles in the same two groups as the page, each alphabetical: Roles (artist composer engineer label musician producer songwriter studio) and Other roles (author host hosting network sponsor), read-only, then "Extra role words" (added to the Roles group). The "Other roles" list is defined in both `PFG_Feed::other_rel_tokens()` and `OTHER_RELS` in pfg-core.js; tests check both against the same literal.
- **Explicit content** (2026-11-13): the checkbox is removed. The Podcast namespace has no explicit tag and requires no tag; `itunes:explicit` is Apple's tag (required only for listing in Apple Podcasts, which does not take publisher feeds). New feeds no longer get `<itunes:explicit>false</itunes:explicit>`. A feed that already has `explicit` true (saved earlier) keeps `<itunes:explicit>true</itunes:explicit>` so its advisory is not lost silently, but it cannot be edited any more.
- **Errors on Save / Download** (2026-11-13): the section holding the first problem opens, its field is focused, and the page scrolls to it (to the message when there is no field). Applies to local validation, a bad feed name, a name already taken and errors returned by the server.
- **itunes:author = Name / title** (2026-11-13, owner, high priority): every feed gets `<itunes:author>` with its Name / title; there is no separate Author value any more (an `author` sent to the server or found in an imported feed is ignored). Same rule in PHP and JS.
- **Settings > Hosted feeds** (2026-11-13): the owner's npub (shortened) is a link to `https://njump.me/<npub>` (opens in a new tab, `noopener noreferrer`). njump is a third-party site; this is the only outside link on that page.
- **Leaving a hosted feed** (2026-11-13): "Back to my feeds" only asks "Leave without saving?" when the user has changed something since the last save (a failed save counts as unsaved; what the Nostr profile filled in does not).
- **pubDate = feed creation date** (2026-11-13/14): each feed has a `created` time (Unix seconds) written as `<pubDate>` just before `<lastBuildDate>`. Hosted feeds: the server sets it when the feed is created (a value sent by the browser is ignored) and it never changes; feeds saved before this use the date the feed record was made. Anonymous feeds: set when the editor opens and kept in the draft, so every download of the same feed has the same pubDate. `created` is a model field handled identically in PHP and JS (a positive whole number below year 2100, else none). An imported feed's `pubDate` becomes its creation date. **Assumption:** "creation date" means the first creation, not the last change (`lastBuildDate` is the last change).
- **Generator tag** (2026-11-14): every feed says `<generator>Phafe RSS Feed</generator>` (was "Publisher Feed Generator"). The plugin and project are still named Publisher Feed Generator; only this feed text follows the owner's wording.
- The **Preview** section is removed. Validation messages still show inline and on Download/Save.
- Roles **songwriter, composer, musician** added to the main list. **Other roles** (author, host, hosting, network, sponsor; sponsor moved there 2026-11-13) get their own heading under it. Both lists are alphabetical (custom tokens sort in with the main roles). The other feed must list the same role tokens for the link to be confirmed.

## Release behaviour (latest requests)
- Payments are **optional**. No recipients = no `podcast:value` block (and no support recipients). With recipients, splits must total 100 minus the support splits.
- Each release card has two states. Empty: one search box (name, or https feed address). Populated (valid GUID + https feed URL): details shown read-only, only the role chips are editable. To change a release, remove it and add again.
- A pasted https address in the search box makes the **server** fetch it (after a Music Index lookup) (`PFG_Lookup::fetch_feed`, `wp_safe_remote_get`). Search calls `https://api.musicindex.org/v1` (`/search`, `/feeds/{guid}`) server-side, cached 1 day per album, rate limited (20 per 5 min per visitor).

## Security model (summary)
HttpOnly SameSite=Strict session cookie `pfg_session`; CSRF header `X-PFG-CSRF`; NIP-98 events (kind 27235, tags u/method/nonce, payload hash when there is a body, within 60 s, nonce single use). Fresh signature in `X-PFG-Auth` is demanded (HTTP 428) for payment-recipient changes and deletes. Feeds are written atomically under uploads with a realpath check; deleted feeds become tombstones so slugs/GUIDs can't be reused. Hosting needs PHP GMP and HTTPS.

The dialog now lists the relays used. (Verified by the owner with Amber, 2026-11-14, after decision 13 below: QR sign-in works.)

Amber has several relay lists (default, connection, profile); the signer must share at least one relay with the QR code. (Verified by the owner with Amber, 2026-11-14: works.)

14. (Item 17, owner request 2026-11-14.) Moving a feed = telling Podcast Index and apps the feed has a new URL. New optional field "New feed URL" (Identity and links), written as `<itunes:new-feed-url>` near the top of the channel; imported feeds that already have the tag now fill the field. Must be https and different from the feed's own URL. The GUID is never changed. The plugin does not move files or redirect: the feed has to stay online at its old address, serving the tag, until apps switch. Assumption: Podcast Index and apps honour `itunes:new-feed-url` for publisher feeds the way they do for podcasts; not tested against them.

15. (Item 23, owner choices 2026-11-14.) Existing publisher feeds on this server can be adopted from Settings, Publisher Feeds, Adopt an existing feed (site admins only; the admin pastes the feed URL and picks the owning account). The URL must be a `folder/name/name.xml` file in this site's uploads folder, be well-formed, have `podcast:medium` publisher and a valid `podcast:guid`. The feed stays at its URL and keeps its GUID (`pfg_legacy_feeds` now maps each slug to its own folder, e.g. `rssfeed/music`); the file is not touched on adoption. The owner then opens it from their feeds: the editor reads the existing file (REST returns `importXml`), fills the form (support recipients lifted as for imports), and the first save rewrites the file from the form like any hosted feed. Before that save, anything the plugin cannot keep (unknown tags, extra attributes, unsupported payment attributes) is listed in a warning with Show what will be removed / Save anyway / Cancel (owner request). Admin suspend/delete/block skip an adopted feed that has not been saved yet, so its original file is never deleted by accident. The first save counts as a payments change, so it needs a fresh signature.

16. (Item 34, owner request 2026-11-15; found while adopting matt_finlay.) `podcast:person` is supported as an editable list in Identity and links (name, role, group, link, image; up to 20; output attributes in the order href, img, group, role). The tags `<podcast:block>no</podcast:block>`, `<category>Music</category>` and `<podcast:complete>no</podcast:complete>` are always written at the end of the channel and are not editable. When reading an existing feed those three are treated as the defaults only when they hold exactly those values; any other value (for example `podcast:block` yes) is listed in the "data will be removed" warning, not silently replaced.

17. (Items 35 and 37, owner choices 2026-11-15.) Browser-key accounts: "Create account" makes a Nostr key in the visitor's browser (localStorage, never sent to the server) and signs the login event with it. There is no backup, restore or password; people wanting a lasting account use a signer or extension. The account records `kind = browser` at creation, set only when the login says so, and never cleared by a later login; the server refuses payment recipients and funding links for those accounts (403 `pfg_payments_locked`), so the lock does not rely on the page. The editor shows the Payments section locked with a message and a "More information" link whose URL is the plugin setting `more_info_url` (https only). The same message shows in a bar under the header on every sign-in with the browser key. Upgrading to a safer signer (item 36) is not built yet.

18. (Item 36, step 2, owner choices 2026-11-15.) "Upgrade my sign-in" (browser-key accounts only): the person connects a signer app or extension and the account moves to that key. Both keys must sign: POST `/me/upgrade` has a body naming only the new key; the old key (the session key) signs a fresh NIP-98 event in `X-PFG-Auth`, the new key signs another in `X-PFG-Auth-New`, both for the upgrade URL, bound to the same body, each with its own single-use nonce. Nothing changes unless both are valid. Feeds belong to the account, so slugs, URLs and GUIDs stay as they are. The account becomes a normal signer account (payments unlock) and the key kept in the browser is removed. If the new key already has an account with feeds the move is refused (no merging); an empty account for the new key is replaced. A failed attempt leaves the browser key signed in.

19. (Item 36, step 3, owner choices 2026-11-15.) Admin "Move a feed to another account" (Settings, Publisher Feeds): for people who lost a browser key or want a feed on a new key. Only the feed's `account_id` changes; file, URL and GUID stay. The new owner (an npub, or hex) need not have signed in before. The plugin checks that the new owner controls the website in the feed (the channel link, read from the file for adopted feeds): their key is listed in `https://<host>/.well-known/nostr.json` (NIP-05), or their npub appears on the feed's website page. Both fetches are https only through the safe HTTP functions. The administrator can tick a box to skip the check when they have confirmed the person another way (the plugin does not record that). Blocked accounts cannot receive feeds.

20. (Item 48, owner request 2026-11-16.) A new hosted feed whose name is reserved, already used (including deleted feeds, which keep their name), recorded as a legacy feed, or already present on disk (a folder or file of that name in the feed folder) is saved under the next free name instead of failing: `test` becomes `test1`, then `test2`, and so on (the base is shortened to stay within 40 characters). The check looks at the real folder, not only the lists. The response and editor show the name that was used. Malformed names are still refused. Adopted and existing feeds are never renamed.

21. (Items 49 and 52, owner choices 2026-11-16.) Moving a hosted feed: the "New feed URL" field is gone from the hosted editor (it stays in the anonymous, self-host editor). "Your hosted feeds" has a "Move feed" button: a window explains that apps will be told the feed moved and that related feeds must be updated, asks only for the new URL (Move / Cancel), then asks "Are you sure you want to move this feed?" and states the KeepMoved period. Confirming calls POST `/me/feeds/{id}/move` (fresh NIP-98 signature, https URL, not the current address), which writes `<itunes:new-feed-url>` and publishes; ordinary saves ignore `newFeedUrl` and keep the stored one. Podping will be sent there when it exists (not built). Adopted feeds that have not been saved in the editor cannot be moved. The date moved is stored in `moved_at` on the feed (DB version 4). Setting `keep_moved_days` (KeepMoved, default 28, 1 to 3650): the admin page shows a notice when feeds were moved more than KeepMoved days ago, highlights them and shows a Moved column. Nothing is deleted automatically; the admin deletes them.

22. (Owner request 2026-11-16.) Suspending a feed (including when an owner is blocked) no longer deletes its file: it is moved to `wp-content/pubfeeds-suspended/` (closed with `.htaccess` and an empty index, and the file name carries a 16-character keyed hash so it cannot be guessed) and the feed row is marked suspended. Unsuspend or approve puts the same file back; if no kept file exists the file is rebuilt from the saved settings. Deleting a feed removes the kept copy too. Feeds adopted from an existing file and not yet saved in the editor are still never suspended or deleted by these actions.

23. (Item 60, owner request 2026-11-17.) Credit invitation: the page reads `?credit=<feed GUID>` (case-insensitive GUID, anything else is ignored). The server looks the feed up in Music Index (POST `/lookup/guid`, rate limited, cached 1 day, 400 for a bad GUID and 404 if unknown). The page then shows "Congratulations! <artist> wants to credit you for your work on <feed title>." (dismissable) on every screen, so it is also seen before sign-in. In the editor's Releases section, before any releases, an "Add <feed title> by <artist>" option adds that release at the top and reads its feed to check the link back; it is hidden while the release is in the feed and offered again if removed. Nothing is saved until the owner saves the feed. The message shows at once as "Congratulations!" / "Someone wants to credit you." (above the in-browser-key reminder) and is replaced by the artist and title when Music Index answers; the editor option appears whenever that data arrives, even after the editor is open, and Dismiss only hides the message. The message is dismissed automatically when the release is already in the feed being edited (or is added). `?roles=Engineer,Mixer` (also repeated `roles=` or `role=`, case-insensitive, unknown names ignored) names roles that are ticked by default when the release is added.

24. (Item 56 and owner request 2026-11-18.) The feed contact email is required for every hosted feed (browser, extension and signer logins alike), checked in both the JS and PHP validators; the anonymous self-host editor keeps it optional. Existing hosted feeds without one must be given an address before they can be saved again. The sign-in window is headed "Get started": name and "Create account" come first (not offered when a key is already kept in this browser), then "Already a user?" / "Sign back into your account", then the sign-in options (This browser if a key is kept, Browser extension, Scan QR code, Paste bunker link). An installed extension is preselected; otherwise no option is preselected.

25. (Owner request 2026-11-18.) The separate "Your hosted feeds" screen is gone. When signed in, the start screen shows "My feeds" (with a "New feed" button and the list) in place of the "Create an account in one click…" card; signed out, that card with "Get started" is shown. The editor's Payments section is headed "Receiving payment".

26. (Owner request 2026-11-18.) "Forget this key" closes and redraws the whole Get started window, so Create account is offered again. In the editor's Receiving payment note for in-browser-key accounts, the link is "More...": it scrolls to the "You are signed in with a key kept in this browser" message and flashes its background green twice (the message itself keeps its "More information" link).

27. (Items 50, 54 and 61, owner requests.) My feeds has no URL column: each row shows the feed name (with its folder name below) and a "Feed URL" button (disabled until the feed is public) that opens a window with the name, the address (read-only, with Copy) and a "Go to Feed URL" link. Each release in the editor has a Collapse / Expand button that folds it down to its heading; saving with an error inside a folded release opens it. The plugin settings page is split into tabs: Hosting (with the uninstall option), Payments, Roles, Hosted feeds and Adopt or move a feed. All settings stay in one form with one Save button (shown on the first three tabs), so saving on any tab saves them all; without JavaScript every section is shown. After a moderation action the page opens on the tab it belongs to, and the address hash (for example #feeds) selects a tab.
