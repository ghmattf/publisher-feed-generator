# Decisions, assumptions and open items

Status: plugin v0.4.1 feature-complete for the agreed scope; all automated checks pass (`tests/run-all.sh`). The owner has tested it on a real WordPress site, with real signer apps and against the live Music Index API, including searching by feed address (all OK, 2026-11-13).

## Product decisions (stated by the owner)
- Versioning: the plugin is at **0.4.1** (0.3.0 on 2026-11-13; 0.2.0 was decided 2026-11-12, replacing an earlier 1.0.0 string that was never tagged or released). Major version changes (including moving to 1.0.0) need the owner's explicit approval. Features and fixes before that are minor/patch bumps (0.3.0, 0.2.1).
- Publisher feeds only (`podcast:medium` publisher). Not albums or tracks.
- Two modes. Anonymous: create, edit, export, no login (paste-XML import was removed from the page on 2026-11-13: the "Edit an existing feed" card and screen are gone, `Core.parseXml` and its tests stay). Hosted: Nostr login (browser extension via NIP-07, or remote signer via NIP-46), feeds hosted on phafe.com.
- Whole-feed import (now not reachable from the page, see above) was by **pasted XML only**. No URL import. Importing into hosting is not an option.
- The `podcast:txt purpose="npub"` value in a feed does not need to match the login key (a convention for this generator only).
- Sign-in options (decided 2026-11-12): browser extension (NIP-07, `window.nostr`, for example Alby or nos2x), pasted `bunker://` link, QR code (NIP-46). The extension tab is first and preselected when `window.nostr` is detected, otherwise last (with a "Check again" button). Still Nostr only. `window.nostr` is looked up on every call, never cached, and only a flag (no key) is kept in `sessionStorage`. The server is unchanged: login and fresh signatures are the same NIP-98 events whichever signer produced them.
- Hosted accounts live in their own table keyed by npub, not WordPress users.
- No cross-feed approval flow: a label etc. sends the exact text (snippet) to whoever controls the other feed.
- No non-Nostr login fallback.
- Roles follow Podcast Index namespace PR #793 (`rel` is a space-separated role set; both sides must list the same set to be confirmed; if one side omits `rel` the link is kept). `studio` and `engineer` are built-in tokens too (2026-11-13), so the role picker offers artist host author label producer network hosting sponsor songwriter composer musician studio engineer; more can be added in Settings.
- `podcast:value method="lnaddress"` is the default payment method (confirmed by the owner, 2026-11-11).
- Project and plugin name is **Publisher Feed Generator** (decided 2026-11-11). Naming scheme: plugin folder/slug and text domain `publisher-feed-generator`, main file `publisher-feed-generator.php`, main class `Publisher_Feed_Generator`, shortcode `[publisher_feed_generator]`, code prefix `pfg` / `PFG_` (classes, constants, options, DB tables `pfg_*`, REST namespace `pfg/v1`, cookie `pfg_session`, headers `X-PFG-*`, JS globals `PFG*`, CSS `.pfg-*`). Nothing was live, so there is no migration from the old `mspf_*` names.
- Website and Image URL accept `http://` as well as `https://` (decided 2026-11-12; Nostr profiles often use http). Every other URL (feed URLs, support link, release feed/image URLs) stays https-only.
- New hosted feed: after Nostr sign-in the form is prefilled from the user's Nostr profile (kind 0): name -> Name / title and Author, about -> Description, website -> Website, picture -> Image URL, lud16 -> one `lnaddress` payment recipient (split 100 minus the platform share), signed-in npub -> Your npub. Only empty fields are filled, only for new hosted feeds, never anonymous mode. `lud06` (LNURL) is ignored. The profile is read by the browser from relays (no server fetch, no signing).
- "Get your npub" button under the npub field: fills from the signed-in account, otherwise asks a signer app for its public key (bunker link or QR), without creating a hosted session, and forgets the signer afterwards.
- "Save and publish" does **not** send a podping. The plugin has no podping code. Not added (it would be a new feature: needs a Podping account/token and a decision on when to ping).
- Example reference feeds (live on phafe.com, read-only for us): `Phafe.xml` (publisher), `mezzaforte.xml` (artist publisher), the album feed `some_songs.xml` (GUID 07adf84f-c1fa-47a7-a121-0fb544e859bd). Updating those feeds is out of scope.

## Editor changes (2026-11-12, owner request)
- **Feed name** is only the file name (`.../<name>/<name>.xml`). It is made from Name / title while the user types (accents removed, `&` becomes "and", max 40, must be a valid name) until the user types their own. Still fixed after saving; a taken name is reported on that field.
- **Category** and **Language** are drop-down lists (lists in `pfg-core.js`: `CATEGORIES`, `LANGUAGES`). A value from an imported feed that is not in the list is kept as an extra option.
- **Author** (`itunes:author`, now not in the form, see below) was the public creator name shown in apps. **Owner** is `itunes:owner` (name + email), a contact for directories, not shown to listeners.
- **Support the developers (optional)**: replaces the fixed platform row and the admin option "apply to exports". Shown in **both modes** (owner answer). Each configured recipient has an editable split 0-99 (default 1); 0 leaves it out. Per feed the model stores `support: [{address, split}]`; the server takes name, address and type from Settings only and ignores unknown addresses. User recipients must total 100 minus the support total; support total must stay under 100. Imported feeds keep exactly their own splits (`liftSupport`). With no own recipients there is no value block. Support splits are part of the payment fingerprint (HTTP 428).
- **Release search**: one search box and the hint "Search by name or paste the feed url above." The paste box and "Read feed" button are gone, so pasting XML into a release is no longer possible. A pasted https address is first looked up in Music Index (exact `feedUrl` match), otherwise the server reads the feed itself. The address is sent to the Music Index search as the normal `q` parameter (tested OK by the owner, 2026-11-13); if it ever finds no exact match, the fallback reads the feed directly.
- **Release heading** reads "<title> by <artist>" when an artist is known (2026-11-13). Artist = the release feed's publisher link with `rel="artist"`, else its first publisher link; the name is our own title if that link is this feed, a `title` attribute on the link if present, otherwise the editor asks the server to read that publisher feed (same fetch as release feeds) and uses its channel title. If none of that gives a name: the Music Index artist from the search result, then the first `podcast:person`. Shown only for releases read or picked in this session, not stored in the feed. **Assumption:** reading the artist's publisher feed is one extra server fetch per release; failures are silent.
- **Artist** is a read-only field at the top of the feed details (display only, not saved). When a release feed already lists this feed with roles, those roles are selected by default if the creator had not chosen any.
- **Feed details** of a release (Title, Type, Feed GUID, Feed URL, Cover image URL) are grouped under a "Show feed details" / "Hide feed details" button, hidden by default; a validation error on any of them opens it.
- **Form sections** (2026-11-13) work as an accordion: only Basics is open at first, opening one closes the others, and every section but the last ends with a Next button that opens the next one. Opening a section by clicking its title also scrolls it to the top, like Next. A failed save/download opens the section with the first error. A Nostr-profile Lightning address no longer opens Payments by itself (the banner says it was filled).
- **Author and Keywords removed from the form** (2026-11-13): nothing in the plugin requires them (only an optional tip existed, now removed). Values already in an imported feed are kept and exported unchanged, but cannot be edited. The Nostr profile name now fills Name / title only. **Owner name / Owner email** are labelled **Feed creator/editor** / **Feed contact email**; the XML is unchanged (`itunes:owner` / `itunes:name` / `itunes:email`), only labels and error messages differ.
- **Start screen** (2026-11-13): the page title is an h1 "Roles feed generator"; the app now has its own background so its text is readable on any site theme (it was white on a yellow theme in dark mode); the intro is one sentence; the first card is "Hosted feeds" with a purple "Get started" button ("My feeds" when signed in); the second is "Want to self-host?" with a plain "Start" button; the "Edit an existing feed" card and screen are removed.
- **Editor changes 2026-11-13 (owner to-do 7-12):** Category field is hidden (the value stays Music; imported or existing values are kept). npub label is "Include npub in the feed? (optional)". Signed in with Nostr, the anonymous editor's address field is labelled just "Feed URL" (assumption: that is what "assume it will be hosted" means; hosted editors already say "Feed URL"). Leaving Basics (Next, or opening another section) is refused until Name / title and Description are filled in; errors show on those fields. A "Generate GUID" button sits under the GUID field: UUIDv5 of the feed URL when there is one, otherwise a random UUID (assumption about what "generate GUID" meant; the GUID still also fills in automatically from the feed URL). The "Downloaded ... Upload it to ..." message shows under the Download button instead of at the top.
- **Settings > Roles** (2026-11-13) shows the built-in roles in the same two groups as the page, each alphabetical: Roles (artist composer engineer label musician producer songwriter studio) and Other roles (author host hosting network sponsor), read-only, then "Extra role words" (added to the Roles group). The "Other roles" list is defined in both `PFG_Feed::other_rel_tokens()` and `OTHER_RELS` in pfg-core.js; tests check both against the same literal.
- **Explicit content** (2026-11-13): the checkbox is removed. The Podcast namespace has no explicit tag and requires no tag; `itunes:explicit` is Apple's tag (required only for listing in Apple Podcasts, which does not take publisher feeds). New feeds no longer get `<itunes:explicit>false</itunes:explicit>`. A feed that already has `explicit` true (saved earlier) keeps `<itunes:explicit>true</itunes:explicit>` so its advisory is not lost silently, but it cannot be edited any more.
- The **Preview** section is removed. Validation messages still show inline and on Download/Save.
- Roles **songwriter, composer, musician** added to the main list. **Other roles** (author, host, hosting, network, sponsor; sponsor moved there 2026-11-13) get their own heading under it. Both lists are alphabetical (custom tokens sort in with the main roles). The other feed must list the same role tokens for the link to be confirmed.

## Release behaviour (latest requests)
- Payments are **optional**. No recipients = no `podcast:value` block (and no support recipients). With recipients, splits must total 100 minus the support splits.
- Each release card has two states. Empty: one search box (name, or https feed address). Populated (valid GUID + https feed URL): details shown read-only, only the role chips are editable. To change a release, remove it and add again.
- A pasted https address in the search box makes the **server** fetch it (after a Music Index lookup) (`PFG_Lookup::fetch_feed`, `wp_safe_remote_get`). Search calls `https://api.musicindex.org/v1` (`/search`, `/feeds/{guid}`) server-side, cached 1 day per album, rate limited (20 per 5 min per visitor).

## Security model (summary)
HttpOnly SameSite=Strict session cookie `pfg_session`; CSRF header `X-PFG-CSRF`; NIP-98 events (kind 27235, tags u/method/nonce, payload hash when there is a body, within 60 s, nonce single use). Fresh signature in `X-PFG-Auth` is demanded (HTTP 428) for payment-recipient changes and deletes. Feeds are written atomically under uploads with a realpath check; deleted feeds become tombstones so slugs/GUIDs can't be reused. Hosting needs PHP GMP and HTTPS.

## Assumptions to verify (not confirmed)
1. (Sites that had saved the old single Podcastindex.org default are upgraded to the three defaults automatically; a customised list is kept.) Default support recipients: Phafe.com (`phafe@phafe.com`), musicindex.org (`heycitizen@getalby.com`), Podcastindex.org (`podcastindex@getalby.com`), 1% each, all `lnaddress`. Owner must review in Settings > Publisher Feeds. A change only affects feeds saved afterwards.
2. (Verified by the owner against the live Music Index API, 2026-11-13.) Music Index detail fields were assumed from the `v4v-musiclink-pro` code; if `feed_url` is absent in a result, the UI asks the user to paste the feed address.
3. The NIP-46 client key is kept in `sessionStorage` so signing works after a reload (XSS would expose it).
4. Cloudflare may cache hosted XML; a purge may be needed after publishing.
5. (Verified by the owner, 2026-11-13: Alby browser extension sign-in and the Amber remote signer both work.) Other extensions (for example nos2x) are untested.
6. Profile lookup relays are `wss://purplepag.es`, `wss://relay.damus.io`, `wss://nos.lol`, `wss://relay.primal.net` plus the relays in Settings. Not tested against live relays (only a fake pool); a profile that lives only on other relays will show "No Nostr profile was found". Not configurable in Settings yet.
